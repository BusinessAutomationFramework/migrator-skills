# /migrator-verify-transfer — рігорозна перевірка переносу

`python -m migrator run` показує "Итого: N, Успешно: M" - але M = N НЕ
гарантує, що дані на боці приймача СПРАВДІ ідентичні джерелу (див.
`/migrator-run-task` про часті причини часткової невдачі). Цей скіл
запускає `scripts/verify_transfer.py` - читає ОБИДВІ бази ЗАНОВО і звіряє
факти: відсутні/зайві записи, польові відмінності, кількість рядків
табличних частин.

## Команда

```powershell
python "${CLAUDE_SKILL_DIR}/scripts/verify_transfer.py" <шлях_до_Migrator> <корінь>:<завдання> --ts-sample 15
```

Приклад:

```powershell
python "${CLAUDE_SKILL_DIR}/scripts/verify_transfer.py" D:\Bukovel\BAF_TOOLS\Migrator bukovel-legacy:warehouse --ts-sample 15
```

Для великих довідників додайте `--limit N`, щоб не читати все двічі під
час діагностики (повна перевірка - без `--limit`, ПІСЛЯ фінального
запуску).

## Як інтерпретувати вивід

### "Відсутні у приймачі" / "Зайві у приймачі"

Якщо джерело - живий, спільний сервер (не статичний тестовий дамп) - НЕ
завжди помилка переносу. Спершу перевірте: чи UUID зайвого запису в
приймачі відповідає ІНШОМУ UUID у джерелі з ТИМ САМИМ найменуванням
(запис міг бути видалений і пересворений на джерелі МІЖ моментом
переносу і моментом перевірки - дрейф даних живої бази, не баг коду).
Якщо ні - це або (а) справжня прогалина переносу (перевірте
`logs/engine/<сесія>/engine.log`/`write_progress.log` на помилки саме
для цього UUID), або (б) залишковий тестовий артефакт з попередніх
запусків (не помилка ЦЬОГО запуску).

### "Відмінності полів (НЕ групові записи)"

Це - реальні відмінності, що ПОТРЕБУЮТЬ пояснення, кожна:
1. Перевірте, чи поле - у списку відомих категорій "очікуваних"
   відмінностей: `ВерсияДанных` (платформа завжди оновлює - вже
   виключено скриптом), формат "порожньої" дати `0001-01-01` (BSL
   `Формат()` дає `""`, COM/.NET `.ToString()` дає `"00010101000000"` -
   ОБИДВА боки зберігають те саме значення, це різниця СЕРІАЛІЗАЦІЇ
   верифікатора, не даних - підтвердьте прямим запитом значення на
   обох боках, якщо не впевнені).
2. Якщо не з відомої категорії - це СПРАВЖНЯ прогалина. Не ігноруйте.

### "Відмінності полів у ГРУПОВИХ записах"

Очікувано - платформа скидає більшість атрибутів для групових елементів
довідника (вони - "папки", не повноцінні елементи). Не потребує дії,
якщо кількість полів із цією категорією РІЗКО не зростає між запусками
(що могло би вказувати на нову, непередбачену проблему).

### "Розбіжностей табличних частин: N з M перевірених"

N > 0 - реальна прогалина ЛИШЕ якщо джерело для цього запису й ЦЬОГО UUID
дійсно існує в приймачі (перевірте спершу "Відсутні"/"Зайві" вище - якщо
UUID відсутній у приймачі, розбіжність табличної частини - НАСЛІДОК
цього, не окрема проблема).

## Якщо знайдено СПРАВЖНЮ прогалину

1. Перевірте бізнес-логіку приймача для цього об'єкта (dump ObjectModule.bsl
   через `db-dump-xml` з `cc-1c-skills`/`baf-skills`, шукайте
   `ПередЗаписью`/`ОбработкаПроверкиЗаполнения` і чи там перевіряється
   `ОбменДанными.Загрузка` - якщо НІ, а перевіряється ВЖЕ ПІСЛЯ раннього
   виходу для завантаження - можливо, потрібен `additional_properties` /
   `ОбменДанными.Загрузка = Истина` на об'єкті ПЕРЕД записом, див.
   Migrator's `docs/schema-format-reference.md`, розділ
   `destination_write_options`).
2. Якщо причина - у ДАНИХ джерела (поле дійсно порожнє в джерелі, а
   приймач вимагає його заповненим) - це прогалина ДАНИХ, не коду
   переносу. Задокументуйте це прямо у `schema.yaml` завдання (коментар
   при відповідному `related_catalogs`/полі), а НЕ намагайтесь
   "обійти" без розуміння призначення бізнес-правила приймача.
