# /migrator-diagnose-write-rejection — чому приймач відхиляє запис

Знайдено емпірично під час acceptance-тесту "Склади" (Migrator): якщо
`migrator run` показує "Итого: N, Успешно: 0" (чи M < N) з помилкою типу
`Error calling context method (Записать): ... поле порожнє чи має
недопустиме значення` - це, як правило, **бізнес-правило ПРИЙМАЧА**
(`ПередЗаписью`/`ОбработкаПроверкиЗаполнения`), НЕ баг парсингу JSON чи
COM (ті дають ІНШІ сигнатури помилок - див. `baf-skills`'
`classic-xml-bsl-gotchas`). НЕ здогадуйтесь про причину - прочитайте
РЕАЛЬНИЙ код приймача.

## Спочатку перевірте СИГНАТУРУ помилки - це два РІЗНІ класи

- `Error calling context method (Записать): ...` - бізнес-правило
  ПРИЙМАЧА (`ПередЗаписью`/`ОбработкаПроверкиЗаполнения`) - йдіть до
  Кроку 1 нижче.
- `Error calling context method (ПредопределенноеЗначение): <Тип>.<Ім'я>.
  <ІмяПредопределенного>. The predefined item is not found in the infobase
  data` - зовсім ІНША причина: елемент задекларований у МЕТАДАНИХ
  приймача, але ще не матеріалізований у ДАНИХ (об'єкт має
  `predefinedDataUpdate: DontAutoUpdate` - платформа сама його не
  створює). Деталі й код виправлення - `baf-skills`'
  `classic-xml-bsl-gotchas`. **Migrator ≥ 1.3.0 вже виправляє це
  автоматично** (`ЗаписатиЕлементи` створює елемент і присвоює
  `ИмяПредопределенныхДанных` сама, якщо `ПредопределенноеЗначение()` не
  знайшла) - якщо помилка досі трапляється, перевірте версію
  `BridgeTool.epf` (`ВерсіяBridgeTool()` у логу старту сесії) і перезбирайте
  за потреби (`/epf-build` з `baf-skills`, база - приймач завдання).

## Крок 1. Витягнути ObjectModule.bsl приймача - ТОЧКОВИЙ dump

НЕ повний дамп конфігурації (гігабайти/хвилини) - лише ОДИН об'єкт:

```powershell
# UTF-8 З BOM обов'язково (див. baf-skills' classic-xml-bsl-gotchas) -
# інакше PowerShell 5.1 спотворить кириличний рядок нижче.
$listFile = "$env:TEMP\migrator_diag_listfile.txt"
[System.IO.File]::WriteAllText($listFile, "Справочник.<Ім'я>`r`n", [System.Text.UTF8Encoding]::new($true))

# ОБОВ'ЯЗКОВО: tasklist /FI "IMAGENAME eq 1cv8.exe" ПЕРЕД цим - див.
# baf-skills' 1c-thick-client-hang-diagnosis.
& "<шлях_до_1cv8.exe>" DESIGNER /F"<шлях_до_бази_приймача>" `
    /DumpConfigToFiles "<тимчасова_папка>" -listFile "$listFile" `
    /Out "<лог_dump>"
```

Результат - `<тимчасова_папка>\Catalogs\<Ім'я>\Ext\ObjectModule.bsl` (для
довідника; `Documents\<Ім'я>\...` для документа).

## Крок 2. Знайти обробники, що можуть відхилити запис

```powershell
Select-String -Path "<тимчасова_папка>\Catalogs\<Ім'я>\Ext\ObjectModule.bsl" `
    -Pattern "ПередЗаписью|ОбработкаПроверкиЗаполнения|ВызватьИсключение|Отказ\s*=\s*Истина" -Context 3,15
```

Прочитайте знайдені процедури ПОВНІСТЮ (не лише збіг рядка) - потрібен
контекст, ЩО саме перевіряється і ЗВІДКИ береться значення (пряме поле?
похідне через інше посилання - як `Владелец.Организация`?).

## Крок 3. Перевірити, чи обробник вже враховує `ОбменДанными.Загрузка`

```powershell
Select-String -Path "<...>\ObjectModule.bsl" -Pattern "ОбменДанными\.Загрузка" -Context 2,2
```

- **Якщо є** (типово на самому початку `ПередЗаписью`: `Если
  ОбменДанными.Загрузка Тогда Возврат;`) - і Migrator ВЖЕ встановлює цей
  прапорець (перевірте версію - з Migrator v1.1.0+ `ЗаписатиЕлементи`
  робить це автоматично на КОЖНОМУ об'єкті ПЕРЕД `Записать()`) - тоді
  причина відмови в ІНШОМУ місці коду (перечитайте `ОбработкаЗаполнения`/
  `ПередЗаписью` ПОВНІСТЮ - можливо, перевірка ВІДБУВАЄТЬСЯ ПІСЛЯ раннього
  виходу для якогось ІНШОГО прапорця, чи в ІНШІЙ процедурі взагалі,
  напр. окремому обробнику `ОбработкаПроверкиЗаполнения`, який платформа
  МОЖЕ викликати незалежно від `ОбменДанными.Загрузка` для деяких типів
  перевірок - тоді дивіться Крок 4).
- **Якщо НЕМАЄ** - оновіть Migrator до v1.1.0+, перезберіть
  `BridgeTool.epf` (`db-dump-xml`/`epf-build` з `baf-skills`), повторіть
  перенос - `ОбменДанными.Загрузка` МАЄ вирішити проблему для БУДЬ-ЯКОГО
  об'єкта, чий обробник перевіряє цей стандартний прапорець (переважна
  більшість добре написаної бізнес-логіки БАФ).

## Крок 4. Якщо причина - у ДАНИХ джерела, не в коді

Якщо перевірка (навіть з `ОбменДанными.Загрузка`) законно ВІДХИЛЯЄ запис,
бо джерело ДІЙСНО не має потрібного значення (напр. джерельне поле
порожнє, а приймач вимагає його ЯВНО, ЗАВЖДИ, незалежно від режиму
завантаження - рідко, але буває для полів, критичних для цілісності) -
це прогалина ДАНИХ, не переносу. Задокументуйте прямо в `schema.yaml`
завдання (коментар при відповідному `related_catalogs`/полі - див.
приклад у `bukovel-legacy:warehouse`'s `schema.yaml`, історія коментарів
про `Справочник.КассыККМ`/`Владелец` перед тим, як знайшли справжню
причину). **Не намагайтесь "вигадати" відсутнє значення** - краще
задокументована прогалина, ніж тихо некоректні дані на боці приймача.
